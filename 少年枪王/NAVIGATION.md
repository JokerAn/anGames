# 寻路缓存与 Bug 复查记录

> 本文件保留 2026-10-10 寻路优化时的基准与测试记录。后续 AI 战斗参数与当前验证结果见 [COMBAT.md](COMBAT.md)，本表不代表后续版本的实时性能。

本轮把“每个敌人各自搜索”改成了“按目标节点共享反向最短路距离表”，并补上移动通行检测。核心实现在 `src/navigation.js`，人机决策在 `src/simulation.js`。

## 为什么可以反向共用

当前地图是静态障碍、双向通道、等代价移动。以玩家或其他被追击角色所在的导航节点为终点，从终点向外运行一次 BFS，就能获得所有可达节点到该目标的最短步数，以及每个节点下一步应该去哪里。追同一目标的多个敌人只需要查询同一张表。

这里共享的是覆盖所有起点的距离表及下一跳，不是某一个敌人的整条可变路线。

当前导航图是 25 × 25 的四邻接网格，每格 2 个世界单位。“最短”指该导航图上的最少边数，不代表连续三维空间里的全局最短曲线。机器人身体半径为 0.48，导航节点和边使用 0.55 的安全间距；运行时只在完整身体可以直线通过时跳过中间路点。

## 缓存层次与失效规则

1. 每张地图建立一次可行走节点、双向边和连通分量。
2. 以地图身份与目标导航节点为键，保存反向 BFS 的距离数组、下一跳数组。
3. 目标仍在同一导航节点时复用；目标跨节点后查询新表。旧表仍可供其他追击者或后来回到该节点的目标使用。
4. 每个机器人保留自己的路线副本和游标。移动、消费路点不会修改其他机器人的缓存。
5. 目标死亡、切换目标、跨目标节点、路线当前段不可通过或持续没有进展时重新取路。路线也会定期重新提取；通常只读已有距离表。
6. 每图最多保留 64 张表，使用 LRU 淘汰最近最少使用的目标。三张地图的距离与下一跳数组合计最多 480,000 字节，约 469 KiB；此数不包含图数据、Map、对象和临时队列。
7. 缓存不包含玩家 ID、队伍、房间对象或角色状态。同一服务器进程内，相同静态地图和目标节点可以跨房间复用；单人游戏的缓存位于自己的浏览器内存中，不跨设备共享。

目前地图定义冻结，不会在对局中改变。以后如果添加可破坏墙体、单向跳台、不同体型或不同通行代价，必须把地图版本 / 移动规则纳入缓存键，或清理受影响缓存。非等代价边应改用相应的最短路算法，而不能继续照搬当前等权 BFS。

## 本轮确认并修复的问题

- **只有通行格缓存，没有结果缓存**：原先每位机器人需要绕路时仍独立 BFS，现在共享反向距离表。
- **矮障碍前停滞**：原先用高于部分矮箱子的视线判断能否直走或停止追击，可能持续隔着箱子射击。现已分别判断射击视线与身体通行，并在枪口被挡住时绕行。
- **靠近路点时过早转弯**：原先在距离路点不足 0.8 时直接消费路点，可能切过障碍角。现在先做身体半径扫掠，再决定是否跳过下一路点。
- **合法位置落在不可通行的格子内**：世界位置和网格中心并不等价。现在只沿无障碍线段连接到可达节点，不把角色直接投影到墙另一侧；无效 / 不可达位置返回空路线。
- **每帧排序所有敌人**：改为线性筛选并限制决策频率，困难约每 0.18～0.224 秒、简单约每 0.32～0.364 秒重新评估。目标死亡会立即重选；每发子弹仍进行实际命中与墙体检测。
- **异常武器名进入规则**：`constructor`、`toString` 等继承属性原先可能被当作武器。现在只接受武器表自己的键，空载荷也能安全规范化。
- **输入超时后突然转身**：原先把输入重置成空对象会把朝向变成 0。现在停止移动、开火和跳跃，同时保留当前朝向。

## 基准结果

环境：本机 Node.js v26.10.0。比较修改前源码快照与修改后实现。所有测试使用相同地图、阵容及固定随机种子。下面衡量逻辑计算，不包含 Three.js 渲染、手机 GPU、网络传输或音效，也不等于实际手机帧率。

**48 个人机 + 2 位真人，仿真 10 秒（600 步）**：预热一轮，再取三轮中位数。寻路和人机行为本身已修复，因此前后角色走位与实际发射次数可能不同；这些数字表示同等初始场景的整体规则耗时变化，并非单一函数的收益。

| 地图 | 修改前 | 修改后 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 积木乐园 | 352.01 ms | 133.86 ms | 62.0% |
| 海港仓库 | 552.44 ms | 149.74 ms | 72.9% |
| 沙漠遗迹 | 363.46 ms | 124.93 ms | 65.6% |

**1,200 个起点请求同一目标节点**：取五轮中位数。新版每轮清空导航缓存，计入首次建图和建表开销；旧版的通行格缓存可保留。每轮新版只构建一张表，其余请求复用。

| 地图 | 修改前 | 修改后 | 建表次数 | 命中 / 请求 |
| --- | ---: | ---: | ---: | ---: |
| 积木乐园 | 12.93 ms | 6.11 ms | 1 | 1199 / 1200 |
| 海港仓库 | 12.41 ms | 5.86 ms | 1 | 1199 / 1200 |
| 沙漠遗迹 | 15.44 ms | 5.28 ms | 1 | 1199 / 1200 |

结果记录在 `test/artifacts/navigation-before.json` 与 `navigation-after.json`，性能数据会随设备与运行时负载变化。可运行 `npm run bench` 查看当前版本的耗时及缓存统计。

## 验证覆盖

- 31 项 Node.js 规则与真实 WebSocket 测试。
- 135 组起终点，与独立 BFS 对比最短步数。
- 同目标多起点共用缓存、路线副本互不污染、目标跨节点、缓存 LRU 上限、地图隔离。
- 90 次随机连续坐标追击：三个地图各 30 次，机器人均能绕行至可射击距离。
- 另外抽样检查三个地图 24,961 个合法位置，均可连接导航图；检查 750 条随机连续坐标路线，起点、路点和终点间均可通行。
- 矮掩体绕行、墙角通行、无效目标、死亡换目标、异常武器名、联机输入超时朝向保留。
- 手机多指移动与开火、三张地图第三人称及自由观察、双客户端对战、换图合作和房主移交浏览器回归。

这些检查覆盖已知问题及本轮改动，不承诺不存在其他边界问题。尚未在实体低端手机上测量帧率与长时间发热。
